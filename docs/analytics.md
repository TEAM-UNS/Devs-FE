# 분석·모니터링 도구 정리

> 이 프로젝트에 붙는 Sentry · GA4 · Amplitude가 각각 무엇이고, 수집이 실제로 어떻게
> 일어나며, 무엇을 직접 정해야 하는지 정리한 문서. 면접에서 설명할 수 있는 수준을 목표로 한다.

---

## 1. 세 도구는 서로 다른 질문에 답한다

| 도구      | 답하는 질문                      | 축     |
| --------- | -------------------------------- | ------ |
| Sentry    | 무엇이 망가졌나                  | 안정성 |
| GA4       | 사람들이 어디서 오고 얼마나 오나 | 획득   |
| Amplitude | 들어온 사람이 안에서 무엇을 하나 | 행동   |

**Mixpanel은 Amplitude와 같은 줄**이다. 제품 분석 도구이고 경쟁 제품이라 보통 둘 중 하나만 쓴다.
PostHog, Heap도 같은 줄이다. 같은 줄끼리는 하나를 고르고, 줄이 다르면 같이 쓴다.

GA4와 Amplitude는 절반쯤 겹친다. 둘 다 이벤트를 받고 페이지 조회를 센다. 그래서 "왜 둘 다
쓰냐"는 질문을 받는다. 통상의 답은 **GA4는 서비스 바깥(유입), Amplitude는 서비스 안(행동)**이다.

### 숫자는 서로 맞지 않는다

광고 차단기가 GA4를 가장 많이 막고 Amplitude도 일부 막는다. Sentry는 상대적으로 덜 막힌다.
세는 기준도 다르다. 세 도구의 수치가 다른 것은 정상이며, 이유를 설명할 수 있으면 된다.

## 2. 수집은 실제로 이렇게 일어난다

`trackEvent('Viewed Dashboard', { prompt_version: 'BA400.4' })` 한 줄이 실제로 나간 모양이다.
(2026-09-26, 빌드 결과물을 브라우저로 열어 요청 본문의 gzip을 풀어 확인)

```json
{
  "api_key": "36895d57...",
  "events": [
    {
      "event_type": "Viewed Dashboard",
      "event_properties": {
        "prompt_version": "BA400.4",
        "[Amplitude] Page Path": "/",
        "[Amplitude] Page Title": "UNS-FE",
        "[Amplitude] Session Replay ID": "ba1d1aa5-.../1790430135250"
      },
      "device_id": "37214ac0-327a-41ff-bd77-24c587d9427f",
      "session_id": 1790429449859,
      "time": 1790429834838,
      "insert_id": "614811c9-...",
      "platform": "Web",
      "language": "ko",
      "ip": "$remote"
    }
  ]
}
```

- 직접 쓴 값은 `event_type`과 `prompt_version` 둘뿐이다. 나머지는 SDK가 붙인다.
- `device_id`는 브라우저마다 생겨 localStorage에 저장된다. 브라우저를 바꾸면 다른 사람으로 센다.
- `session_id`는 시각 숫자다. 기본값 기준 30분간 이벤트가 없으면 새 세션이 된다.
- `ip: "$remote"`는 서버가 받은 IP를 쓰라는 뜻이다. 지역 정보가 여기서 나온다.
- `insert_id`는 중복 제거용이다. 재전송돼도 한 번만 집계된다.
- 여러 이벤트가 한 배치로 묶여 나가고, 본문은 gzip으로 압축된다.
  **디버깅할 때 본문이 깨져 보이면 압축 때문이다.** 풀어서 봐야 한다.

### 자동으로 잡히는 층과 직접 심는 층

셋 다 두 층이 있다. 비율만 다르다.

- **Sentry**: 아무도 잡지 않은 에러는 자동. 단 소스맵과 "잡힌 에러 보고"는 직접 해야 한다(§4).
- **GA4**: 향상된 측정으로 페이지 조회·스크롤·외부 링크·다운로드가 자동. 전환은 직접.
- **Amplitude**: `autocapture: true`로 조회·클릭·폼·세션이 자동. 제품 관점의 순간은 직접.

**직접 심어야 하는 것의 기준**은 "자동으로는 의미를 알 수 없는 순간"이다.
버튼이 눌렸다는 자동으로 잡히지만, 가입이 성공했다는 서버 응답을 받은 자리에서만 알 수 있다.

### SPA 주의점

화면이 자바스크립트로 바뀌는 앱은 첫 진입만 페이지 조회로 잡히고 이후 이동이 누락되기 쉽다.
GA4를 GTM으로 붙일 때 브라우저 기록 변경을 조회로 칠지 따로 설정해야 한다.

## 3. 문법은 사실 세 개뿐이다

```ts
// 1. 무슨 일이 일어났다 — 이벤트 속성은 그 순간에 붙는다
amplitude.track('Signed Up', { major: 'FRONTEND', step_count: 4 })

// 2. 이 사람은 누구다 — 로그인 성공 시점에 부른다
amplitude.setUserId('user_1234')

// 3. 이 사람은 어떤 속성을 가졌다 — 이후 모든 이벤트에 따라다닌다
amplitude.identify(new amplitude.Identify().set('plan', 'free'))
```

**이벤트 속성과 사용자 속성의 차이가 중요하다.** "가입 당시 전공"은 이벤트 속성이고
"현재 전공"은 사용자 속성이다. 섞으면 나중에 "전공을 바꾼 사람의 과거 행동"을 셀 수 없다.

GA4를 GTM으로 붙이면 문법이 다르다. SDK를 직접 부르지 않고 배열에 밀어 넣는다.

```js
window.dataLayer.push({ event: 'sign_up', method: 'email' })
```

GTM 콘솔에서 "`sign_up`이 오면 GA4로 보내라"를 설정한다. **코드와 설정이 분리되는 것**이
GTM의 존재 이유다. 대신 콘솔을 보지 않으면 무엇이 수집되는지 코드만으로는 알 수 없다.

이름 규칙도 다르다. Amplitude는 `Viewed Dashboard`처럼 쓰고 GA4는 `view_dashboard`처럼 쓴다.

## 4. 이 저장소의 현재 상태

### Amplitude — 작업 중

```
main.tsx
  initAmplitude()                     ← 키 확인 후 한 번만 초기화
       │
shared/analytics/amplitude.ts
  initAll(key, { autocapture: true, sessionReplay: { sampleRate: 1 } })
       │
  autocapture + 세션 리플레이 시작
```

- 키는 `VITE_AMPLITUDE_API_KEY`. 없으면 경고만 남기고 초기화를 건너뛴다.
- 제품 의미를 담은 세부 이벤트는 지금 추가하지 않고, 추후 이벤트 기준을 정한 뒤 수집한다.
- 이벤트가 실제로 도착하는 것까지 확인했다(§2의 본문).
- **초기 로드 JS가 gzip 기준 142KB → 259KB로 늘었다.** 대부분 세션 리플레이(rrweb)다.
  `sampleRate`를 낮춰도 이 용량은 줄지 않는다. 샘플링은 전송량과 요금에만 영향을 준다.

### GA4 — 코드만 들어갔고 데이터는 안 쌓인다

- GTM 스니펫은 `index.html`에 있고 develop에 머지됐다(PR #44).
- **컨테이너 `GTM-T9PDK3DJ`가 비어 있다.** 스니펫만 있는 페이지로 확인했더니 컨테이너는
  내려오는데 GA4 수집 요청이 0건이었다. 콘솔에서 GA4 태그를 만들고 게시해야 한다.
- `main`에는 아직 없다. 이 저장소는 develop → main 머지가 배포다.

### Sentry — 꺼져 있다

- `@sentry/react`는 설치돼 있고 `app/observability/sentry.ts`도 있지만 `VITE_SENTRY_DSN`이
  비어 있어 초기화를 건너뛴다.
- **DSN만 넣으면 끝이 아니다.** 지금 구조에서 빠진 것이 셋 있다.
  1. **소스맵 업로드**. `vite.config.ts`에 `sourcemap` 설정도, `@sentry/vite-plugin`도 없다.
     없으면 스택이 `DashboardPage-D4sRZJKT.js:1:1911` 같은 모양으로만 남는다.
  2. **잡힌 에러 보고**. react-router 기본 에러 화면이 받아낸 에러는 `window.onerror`까지 가지
     않아 Sentry가 모른다. `Sentry.captureException`이 코드에 한 곳도 없다.
  3. **API 실패 보고**. 요청 실패는 토스트만 띄우고 끝난다.

## 5. 정해야 하는 것 — 그리고 그 판단에 필요한 지식

| 정할 것                                    | 알아야 하는 것                                                 |
| ------------------------------------------ | -------------------------------------------------------------- |
| 이벤트 이름 규칙을 도구별로 둘지 통일할지  | 각 도구의 관례, 나중에 이름을 바꾸면 과거 데이터가 갈린다는 점 |
| 무엇을 직접 심을지                         | autocapture가 무엇을 자동으로 잡는지                           |
| autocapture를 켤지 끌지                    | 자동 수집 항목, 그 안에 입력값·식별자가 섞일 수 있는지         |
| `setUserId`를 언제 부를지                  | 익명 기기 식별과 로그인 사용자 식별이 어떻게 이어지는지        |
| 세션 리플레이를 쓸지, 쓴다면 무엇을 가릴지 | 기본 마스킹 범위, 어떤 화면에 개인정보가 있는지                |
| Sentry 추적 샘플링 비율                    | 샘플링이 비용·정확도와 어떻게 맞바뀌는지                       |
| URL에 무엇을 보낼지                        | 경로에 식별자가 들어가는지, 쿼리에 입력값이 실리는지           |

## 6. 판단 예시 — 다른 프로젝트(체크인 서비스)의 기록

아래는 **다른 사람이 다른 서비스에서 내린 판단**이다. 결론을 그대로 가져오면 안 되고,
"이 판단을 하려면 무엇을 알아야 했는지"를 읽는 용도로 둔다.

1. **"Amplitude는 Mixpanel과 역할이 겹쳐 제외했다"**
   → 같은 줄의 도구를 둘 다 두지 않는다는 판단(§1). 이미 Mixpanel 이벤트 설계가 있었다는 맥락이
   근거다. 이 프로젝트는 반대로 Amplitude만 있고 Mixpanel이 없으므로 같은 결론이 나오지 않는다.

2. **"Sentry Session Replay는 쓰지 않았다. 이름·전화번호 입력 화면이 있어서"**
   → 리플레이의 기본 마스킹 범위를 알아야 내릴 수 있는 판단이다. UNS도 회원가입에 이메일·이름이
   들어가므로 **Amplitude 리플레이 100%를 그대로 둘지 같은 질문이 그대로 걸린다.**

3. **"Mixpanel autocapture는 껐다. 불필요한 이벤트와 개인정보 노출 가능성 때문"**
   → 자동 수집이 무엇을 잡는지 알아야 한다. 끄면 데이터가 깔끔해지지만, 직접 심지 않은 것은
   영영 없다. 지금 UNS는 켜져 있다.

4. **"GA4에는 쿼리스트링·입력값을 보내지 않고 정규화된 path만 보냈다"**
   → 상세 페이지 URL에 id가 들어가면 그게 그대로 분석 도구에 남는다는 것을 알아야 한다.
   UNS는 지금 경로에 식별자가 없지만, 기업 상세나 마이페이지가 생기면 같은 문제가 생긴다.

5. **"Sentry trace sample rate를 0.1로 뒀다"**
   → 성능 추적은 전부 보낼 필요가 없고 비용이 든다는 것을 알아야 한다. UNS의
   `sentry.ts`는 지금 `tracesSampleRate: 1.0`이고 주석에도 "프로덕션에서는 0.1~0.2 권장"이라고
   적혀 있다. DSN을 채우는 시점에 같이 정할 것.

## 7. 면접에서 물어볼 만한 것

- GA4와 Amplitude를 둘 다 쓴 이유는 무엇인가
- 이벤트 이름과 속성은 어떤 기준으로 정했나
- 세션 리플레이를 켠 이유는 무엇이고 개인정보는 어떻게 다루나
- 이벤트가 실제로 도착했는지 어떻게 확인했나
  → 압축된 요청 본문을 풀어 `Viewed Dashboard`와 속성을 눈으로 확인했다(§2)
- 분석 도구를 넣으면서 성능은 어떻게 봤나
  → 초기 로드 gzip 142KB → 259KB를 측정했고, 무엇 때문에 늘었는지 청크 단위로 확인했다
- 세 도구의 숫자가 다르면 무엇을 믿나
