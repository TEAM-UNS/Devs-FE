# ECharts 도입 측정 — 번들 · 렌더러 선택

> 측정일 2026-08-02 · 대상 `feature/dashboard` (대시보드 막대·영역 그래프)
> 기준선 커밋 `d43d869` (차트 도입 직전, 그래프 자리는 빈 박스)

## 왜 쟀나

대시보드 그래프를 ECharts로 구현하면서 두 가지를 정해야 했다.

1. tree-shaking 진입점(`echarts/core` + `use()`)을 쓰는 게 실제로 얼마나 이득인가
2. renderer를 canvas / svg 중 무엇으로 할 것인가

둘 다 "느낌"으로 정하지 않기 위해 조합별로 빌드해 gzip을 재고, 브라우저에서 렌더 비용을 쟀다.

## 1. 번들 크기

`DashboardPage` 청크(라우트 단위 코드 스플리팅 대상). raw는 minify 후, gzip은 level 9.

| 구성                                                     |        raw |          gzip | 기준선 대비 |
| -------------------------------------------------------- | ---------: | ------------: | ----------: |
| **기준선** (ECharts 없음, `d43d869`)                     |    7.90 KB |   **2.70 KB** |           — |
| tree-shaking 없음 (`import * as echarts from 'echarts'`) | 1104.46 KB | **363.18 KB** |  +360.48 KB |
| canvas + svg 등록 (도입 시점 구성)                       |  537.31 KB | **181.61 KB** |  +178.91 KB |
| svg만 등록                                               |  523.81 KB | **177.17 KB** |  +174.47 KB |
| canvas만 등록                                            |  516.45 KB | **173.66 KB** |  +170.96 KB |

읽은 것:

- **tree-shaking이 gzip 363.18 → 181.61 KB (−50.0%)** 를 만든다. 전체 진입점을 쓰면 안 쓰는 차트까지 전부 들어온다.
- **renderer 하나만 등록하면 gzip 7.95 KB(−4.4%)** 를 더 줄인다. 둘 다 등록한 건 비교 측정을 위한 한시적 구성이다.
- canvas와 svg 렌더러 자체의 크기 차이는 gzip 3.51 KB로 작다.
- 그래도 **ECharts는 이 페이지 번들의 대부분을 차지한다.** 기준선 2.70 KB → 173.66 KB는 64배다.

재현:

```bash
git checkout d43d869 && pnpm build   # 기준선
```

## 2. 렌더 비용 (init + setOption)

같은 옵션으로 12회 반복해 중앙값. Vite dev 빌드라 절대값은 프로덕션과 다르며, **상대 비교용**이다.

| 차트                | canvas |    svg |
| ------------------- | -----: | -----: |
| 막대 (9개)          | 6.1 ms | 4.5 ms |
| 영역 (4계열 × 15점) | 4.9 ms | 5.1 ms |

**현재 데이터 양에서는 둘의 차이가 노이즈 수준이다.** 렌더러 선택의 근거가 되지 못한다.

## 3. 데이터가 커질 때 (막대 개수를 늘려가며)

|  막대 수 | canvas ms | svg ms | canvas DOM 노드 | svg DOM 노드 |
| -------: | --------: | -----: | --------------: | -----------: |
| 9 (현재) |       4.7 |    4.0 |               2 |           68 |
|       50 |       7.5 |    8.4 |               2 |          355 |
|      200 |      17.8 |   23.5 |               2 |        1,405 |
|     1000 |      78.1 |   99.3 |               2 |        7,005 |

읽은 것:

- **canvas의 DOM 노드는 데이터 양과 무관하게 2개로 고정**이다. svg는 막대당 약 7개씩 선형으로 늘어난다.
- 렌더 시간은 200개부터 canvas가 앞서고, 1000개에서 **svg가 27% 느리다**.
- 뒤집어 말하면 **50개 이하에서는 차이가 없다.**

## 4. 접근성은 렌더러 문제가 아니었다

처음엔 "svg는 텍스트가 DOM에 남으니 접근성에 유리하다"고 봤는데, 실제 출력을 열어보니 아니었다.

SVG 렌더러로 그린 막대 차트의 DOM에는 **ARIA 속성이 하나도 없다** (`role`·`aria-label`·`<title>`·`<desc>` 전부 없음).
남는 텍스트는 축 라벨 9개뿐이고 **값은 하나도 없다.** 스크린리더는 맥락 없는 기술 이름 나열만 읽는다.

ECharts에는 `AriaComponent`가 있고 이걸 등록하면 컨테이너에 설명이 붙는데,
**canvas와 svg 모두 동일하게 동작한다.** 즉 접근성은 렌더러 선택 기준이 아니다.

> 현재 `AriaComponent`는 등록하지 않았다. 접근성을 챙기려면 별도로 붙여야 하고,
> 기본 문구가 영어 + 내부 비율값이라 `aria.label.description`으로 직접 써야 한다.

## 5. 결정 — canvas

**결정을 가른 건 성능도 접근성도 아니라 시각 표현이었다.**

SVG 렌더러는 `blendMode: 'screen'`을 출력에 반영하지 않는다. zrender 요소에는 설정이 남아 있지만
SVG 마크업에 `mix-blend-mode`가 전혀 나오지 않아, 급상승 그래프에서 **영역이 겹칠 때 밝아지는
Figma 표현(288:987)이 사라진다.** canvas는 `globalCompositeOperation`으로 정상 적용된다.

| 기준                    | 판단                              |
| ----------------------- | --------------------------------- |
| 렌더 성능 (9개 규모)    | 차이 없음 — 근거가 못 됨          |
| 접근성                  | 렌더러 무관 (`AriaComponent`)     |
| 번들                    | canvas가 3.51 KB 작음 — 작은 차이 |
| **겹침 블렌드(screen)** | **canvas만 됨 → 결정 근거**       |

확정 후 실측: `DashboardPage` **516.43 KB raw / 173.94 KB gzip** (둘 다 등록했을 때보다 −7.7 KB).

### 딸려온 변경 — 테스트 전략

canvas는 jsdom에 2D 컨텍스트가 없어 테스트에서 차트를 띄울 수 없다. 그래서 검증 지점을 옮겼다.

- 조립 테스트(`DashboardOverview.test.tsx`)는 `useEChart`를 대체한다. 여기서 볼 것은 "무엇을 어떻게
  조립했는가"이고, 그려진 픽셀은 ECharts의 책임이다.
- 대신 **옵션 빌더를 유닛 테스트**한다(`utils/*.test.ts`). 축 라벨·막대 높이·스텁 처리·그라디언트·
  애니메이션 지연, 그리고 **툴팁이 어느 시리즈를 고르는지**까지 순수 함수로 직접 검증한다.

결과적으로 렌더러에 의존하던 검증(2개)이 렌더러와 무관한 검증(15개)으로 바뀌었다.

## 남은 것 (미측정)

- **초기 페인트 / LCP** — 인앱 프리뷰가 화면을 합성하지 않아 이 환경에서 잴 수 없다. 실제 브라우저에서 Lighthouse나 `reportWebVitals`로 재야 한다.
- **동적 import 효과** — ECharts를 라우트 진입 시점이 아니라 차트가 보일 때 불러오면 초기 로드에서 뺄 수 있다. 아직 안 쟀다.
- `TooltipComponent`는 급상승 그래프에만 쓰는데 두 차트가 같은 진입점을 공유해 항상 포함된다.
